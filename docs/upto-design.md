# `upto`: how it would plug in (design note, not built)

> 2026-09-21. Decision from the B-phase plan: **record the design, do not implement**. Every package fact below was checked against `node_modules/@x402/evm` 2.26.0 (the `.d.mts` files named inline); the ecosystem facts (x402.org support list, the mechamanda endpoint) were true when looked up and must be re-verified before anyone acts on them. Linked from the technical report §17.

## 1. What `upto` is

`exact` moves a fixed amount with one EIP-3009 `transferWithAuthorization`. `upto` lets the payer sign a **maximum** and the payee charge the **actual**:

- The payer signs a Permit2 `PermitWitnessTransferFrom` (domain `Permit2`, `verifyingContract` = `PERMIT2_ADDRESS` `0x000000000022D473030F116dDEE9F6B43aC78BA3`) whose `permitted.amount` is the offer's `amount` (the cap), `spender` is the **x402UptoPermit2Proxy** `0x4020A4f3b7b90ccA423B9fabCc0CE57C6C240002`, and whose witness is `{to: payTo, facilitator, validAfter}`. Types: `uptoPermit2WitnessTypes`, addresses: `x402UptoPermit2ProxyAddress` / `PERMIT2_ADDRESS`, all exported from `@x402/evm` (`dist/esm/index.d.mts` line 5, defined in `constants-CEiC_81n.d.mts`). The payload shape is `UptoPermit2Payload` (`types-BBC1mC8d.d.mts`): `{signature, permit2Authorization: {from, permitted:{token, amount}, spender, nonce, deadline, witness}}`. The nonce is a random 256-bit Permit2 unordered nonce (`createPermit2Nonce`), `validAfter` is `0`, `deadline` = now + `maxTimeoutSeconds`.
- **The signature binds the facilitator's address** (`witness.facilitator`). The offer must therefore carry it: `extra.facilitatorAddress`, which the facilitator's `UptoEvmScheme.getExtra()` supplies (`upto/facilitator/index.d.mts`); the client throws without it (`createUptoPermit2Payload`). A payee cannot later move the settlement to another facilitator, and a payer cannot be settled by anyone but the one it signed for.
- Offers look like `{scheme: 'upto', extra: {name, version, assetTransferMethod: 'permit2', facilitatorAddress}}`; the server-side `UptoEvmScheme` (`upto/server/index.d.mts`) has `defaultAssetTransferMethod` `permit2` and `paymentFlows.permit2 = {supported: ['authorization'], default: 'authorization'}`.
- The payee reports the actual price **before responding**: `setSettlementOverrides(res, {amount})` from `@x402/express` (`express/dist/esm/index.d.mts` line 84). `SettlementOverrides.amount` (`@x402/core`, `x402Client-*.d.mts` line 358) takes atomic units (`"500"`), a percent of the cap (`"33.33%"`, floored) or a dollar price (`"$0.05"`). The middleware pulls it off the response and passes it to `settlePayment(..., settlementOverrides)`.
- The facilitator (`@x402/evm/upto/facilitator`) verifies `permitted.amount == requirements.amount` and refuses a settlement amount above the cap, then calls the proxy for the actual amount and returns **`SettleResponse.amount`** ("actual amount settled in atomic token units. Present for schemes like `upto`", `@x402/core` `x402Client-*.d.mts` line 1416). Failure reason is `invalid_upto_evm_transaction_failed`. It carries a `pendingSettlementStore` so a retried `/settle` reconciles against an already-broadcast transaction instead of re-broadcasting (same shape as our payee's retry in b74c128).

## 2. Wallet changes (`packages/wallet`)

1. **Register the scheme beside exact.** `wallet.ts` line 326 registers only `registerExactEvmScheme`. Add `client.register(network, new UptoEvmScheme(signer, {rpc}))` with `UptoEvmScheme` from `@x402/evm/upto/client` (`upto/client/index.d.mts`; constructor `(signer: ClientEvmSigner, options?: EvmSchemeOptions)`). The base flow still only needs `signTypedData`, so the KMS story in §17.3 of the report does not change.
2. **`isPayableOffer` accepts permit2 when the mandate allows upto.** `offers.ts` line 54 hard-codes `assetTransferMethod` ∈ {undefined, `'eip3009'`} and `scheme === 'exact'`. Extend `PayableScope` with `allowUpto`; when true an offer with `scheme: 'upto'`, `assetTransferMethod: 'permit2'` and a well-formed `extra.facilitatorAddress` is payable. Same `chooseOffer` ordering rule (first supported offer under the validity cap): a payee listing both exact and upto is paid exact unless upto is listed first, which is the payee's choice and is fine.
3. **Gate on the max, book the actual.** `gateAndReserve` reserves `amount` (the cap) — that is correct: the payer is liable for up to the cap until settlement. After the response, `fetch()` reads `SettleResponse.amount` from `PAYMENT-RESPONSE` and books that against the mandate chain, releasing the difference. A missing `amount` on success books the cap (never under-book).
4. **Ledger rows** (`ledger.ts` `LedgerEntry`) gain `scheme: 'exact' | 'upto'`, `maxAmount` and `settledAmount`; `amount` keeps meaning "what was booked" so the wallet page and `wallet_history` need no change. `nonce` stays the row key: for upto it is the Permit2 nonce, a decimal string rather than a 32-byte hex, so the key becomes `string` and `NONCE_HEADER` carries it verbatim.
5. **Reconcile.** Exact rows ask `authorizationState(payer, nonce)` on the token (`wallet.ts` line 769). Upto rows ask Permit2's `nonceBitmap(owner, nonce >> 8)` on `PERMIT2_ADDRESS` and test bit `nonce & 0xff` (Permit2 `SignatureTransfer` unordered nonces; not wrapped by the package, so the wallet carries the two-entry ABI itself, like the EIP-3009 slice in `packages/core/src/eip3009.ts`). Bit set = settled; the **amount** comes from the token's `Transfer(from=payer, to=payTo)` log in the same block range, since the bitmap says nothing about value — that is what makes `settledAmount` verifiable without trusting the payee's `PAYMENT-RESPONSE`. Unused bit past `deadline` = expired, as today.
6. **Permit2 approval without ETH.** Permit2 needs a one-time ERC-20 `approve(PERMIT2_ADDRESS, max)` from the payer. USDC on Base is EIP-2612, so if the facilitator advertises the `eip2612GasSponsoring` extension (key `"eip2612GasSponsoring"`, `chunk-KEX4SYHV.mjs` line 59; `erc20ApprovalGasSponsoring` is the fallback for non-2612 tokens) the client signs a permit that the facilitator submits with the settlement — no ETH in the payer EOA, which is the constraint the whole wallet is built around. This path needs `readContract` on the signer or `options.rpc` (allowance and `nonces` lookups), i.e. the wallet's existing `rpcUrl`. Without the extension: gas once (`createPermit2ApprovalTx` / `getPermit2AllowanceReadParams`, exported from `@x402/evm/upto/client`), and `balance()` should report the allowance so the operator sees it.
7. **Mandate flag** `allowUpto?: boolean`, default **false**, on `IntentMandateInput` / `IntentMandate` (`mandate-store.ts`), validated on delegation (a child cannot enable what the parent disabled) and shown on the approval card. Default off because an upto offer's cap is what the policy gate sees; a human approving "$5 for market data" should opt in to payees that may charge less than they reserve.

## 3. Payee side (`packages/payee`)

- `server.register(network, new UptoEvmScheme())` from `@x402/evm/upto/server`, opt-in per paywall (`paywall.ts` line 108 registers exact directly; upto goes beside it, never instead).
- `charge('$0.05', {upto: true})` publishes the price as the cap; the handler computes the actual and calls `setSettlementOverrides(res, {amount})` **before** sending headers (the middleware reads it after the handler, before `/settle`).
- In-flight key: `inflightKey` (`paywall.ts` line 22) reads `payload.authorization.{from,nonce}`; an upto payload has `payload.permit2Authorization.{from,nonce}`, so the key becomes `from:permit2nonce`. The settle lock and unused-authorization retry (b74c128) apply unchanged; "unused" is the `nonceBitmap` bit instead of `authorizationState`.

## 4. Facilitator

Our own facilitator would register `@x402/evm/upto/facilitator`'s `UptoEvmScheme` (constructor `(signer: FacilitatorEvmSigner, config?)`); it needs the **x402UptoPermit2Proxy deployed on the chain** (the package hard-codes one address, so a chain without it cannot do upto at all). The hosted x402.org facilitator listed `upto` on `eip155:84532` at the time of writing (`/supported`); re-check before relying on it.

## 5. First target and acceptance

**mechamanda's Base Sepolia upto simulation endpoint** (found via the CDP Bazaar; re-verify URL, price cap and `facilitatorAddress` with `agentpay discover --network eip155:84532` and a plain `agentpay offer` before spending). Accepted when, against that endpoint with the `.local/` Base Sepolia wallet: (a) `agentpay offer` shows `upto`/`permit2` and the wallet refuses it with `unsupported_offer` while `allowUpto` is off; (b) with `allowUpto` on, the first `pay` either rides `eip2612GasSponsoring` or reports the one-time approval clearly; (c) `pay` succeeds, the ledger row shows `maxAmount` > `settledAmount` = `SettleResponse.amount`, and the mandate's remaining budget reflects the actual; (d) `reconcile` marks the row `verified` from `nonceBitmap` + the Transfer log with the same amount; (e) the exact-only test suites are untouched and still green.

## 6. Why deferred

Every US-equity data seller found in the x402 ecosystem (Massive, x402stock, tickersfeed, OttoAI, the EDGAR apitoll, x402atlas) sells `exact` at a fixed per-call price on Base mainnet; the only upto payee is a simulation. Kairos buys bars and news at a known price, so a cap-then-actual scheme buys nothing today while touching the wallet's reservation, ledger and reconcile invariants. This note keeps the design so the change stays a day's work when a seller worth paying quotes `upto`.
